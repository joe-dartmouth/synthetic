# `bko.ontology`: ontology loading and field mapping

Load MONDO, HPO and DO from pinned OBO releases with pronto, and map their concepts to dataset fields, starting with the disease label and chest-pain type. Each mapping records its source, encoding and limits; numeric fields are governed by separately specified range constraints, defined with their frame in `bko.datasets` and re-exported by `bko.ontology.mapping`; concepts with no defensible field are out of scope, and the near misses are listed with their reasons. The same table maps Synthea's SNOMED-CT condition codes to the MONDO concepts the release equates with them, and lists the codes it excludes with their reasons. `bko.ontology.icd9` maps Diabetes 130's ICD-9 diagnosis categories to the MONDO concepts carrying their xrefs, with every live holder declared, and its two lab fields' result states to HPO phenotypes, and lists the categories it excludes with their reasons. `bko.ontology.icd9_codes`, written by `bko.ontology.codes` (`python -m bko.ontology codes`), maps each exact diagnosis code of the archive to the one MONDO concept that carries its xref, for the `diabetes-codes` frame (ADR [`research/diabetes-diagnosis-codes`](../../../docs/adr/research/diabetes-diagnosis-codes.md)). `bko.ontology.frames` holds the Synthea and Diabetes 130 frames, their indicators and their field rows, built from `bko.ontology.mapping` and `bko.ontology.icd9`, so any stage may read them. `bko.ontology.code_frames` builds the `diabetes-codes` frame from its loaded records and holds its field rows, one per generated code row and diagnosis column.

The loader returns standard-library values, so no other stage imports pronto. The releases are pinned in `bko.datasets.sources`, and the rows are typed constants in `bko.ontology.mapping`. ADR [`research/ontology-mapping-design`](../../../docs/adr/research/ontology-mapping-design.md) records the design, and [`docs/DEVELOPMENT.md`](../../../docs/DEVELOPMENT.md#ontologies) the command that checks the table against the releases. No row has had clinician review, which the plan makes conditional on availability ([RESEARCH, Represent](../../../docs/RESEARCH.md#represent)). Loaded releases convert to BKB fragments in `bko.ontology.fragments` (ADR [`research/bko-fragment-encoding`](../../../docs/adr/research/bko-fragment-encoding.md)). `bko.ontology.fragments.scope_of` gives the classes a release's fragment holds for some mapped concepts, and `bko.ontology.releases.load_releases` fetches and loads the pinned releases a command reads. `bko.ontology.santos` rebuilds Santos et al.'s MONDO/DO fusion example from the pinned releases ([`docs/DEVELOPMENT.md`](../../../docs/DEVELOPMENT.md#fusion-reproduction)). `bko.ontology.elk` classifies the pinned MONDO and HPO OWL releases with ELK through the pinned ROBOT jar, which needs a JDK, and lists each ancestor pair within the mapped concepts and their ancestors that the classification or the loaded OBO release holds and the other lacks (`python -m bko.ontology elk`, [`docs/DEVELOPMENT.md`](../../../docs/DEVELOPMENT.md#elk-comparison)); ROBOT runs as a Java subprocess the gate never runs, no module parses OWL in Python, and `elk.read_hierarchy` reads ROBOT's classified OBO output, which pronto refuses for HPO. `bko.ontology.convert` converts an OWL-only release, a `Source` whose `filename` ends `.owl`, to OBO with the same jar's `convert` when `load_releases` first reads it, after refusing an OWL file that names an import; the OBO sits beside the OWL in its snapshot directory, named for the jar's sha256 so a re-pinned jar converts again, and each load logs its size and sha256 ([`docs/DEVELOPMENT.md`](../../../docs/DEVELOPMENT.md#ontologies)).

- **Dependencies:** The `ontology` extra (`pyproject.toml`), `bko.datasets` with its `data` extra, and `bko.bkb`.
- **Status:** built.
